Feature under review: `POST /summarize-claim` (`app/claims.py`), running against
`RETRIEVAL_MODE=hybrid_bm25_rrf` (Week 4's fix, already shipped) and the

to a question.

## Redaction

**Claimant names and claim numbers are redacted before the trace is written,
not after.** `app/tracing.py`'s `build_trace_record()` is the only function
that constructs a `TraceRecord`, and it calls `redact_notes()` on the input
and masks the claim-number field in the output before either value is ever
assigned to the object that gets serialised — there is no unredacted
intermediate that touches `write_trace()`. `read_traces()` over the committed
`traces.log` confirms every stored record's `input_redacted` field already
contains `[CLAIM NUMBER REDACTED]` / `[CLAIMANT NAME REDACTED]` in place of
the real values.

## Replay evidence

Replayed trace: **`trc_00081`** (picked by the same seeded RNG, continuing
from the sample draw). Replay reconstructs the retrieved chunks from the
fields stored *in the trace* — chunk id, doc id, filename, page, section
path, score, and text — and re-runs `ClaimSummaryGenerator.summarize()`
against them. No live vector store or original PDF was read.

| field | original (stored) | replayed | match |
|---|---|---|---|
| `claim_number` | `[CLAIM NUMBER REDACTED]` | `UNKNOWN` | **no** |
| `date_of_loss` | `09 July 2026` | `09 July 2026` | yes |
| `coverage_decision` | `denied` | `denied` | yes |
| `cited_exclusion_id` | `4.1` | `4.1` | yes |
| `excess_amount` | `250000.0` | `250000.0` | yes |
| `summary` | *(stock-below-floor exclusion sentence)* | *(identical)* | yes |
| `citations` | `["4fa131d2878b9fbf::0001"]` | `["4fa131d2878b9fbf::0001"]` | yes |

**Every field replays exactly except `claim_number`, and that gap is
structural, not a bug.** The claim number was masked out of the *input*
before the trace was written, and the stub's claim-number extraction is a
regex over that input text — replaying from the redacted trace alone gives
the extractor nothing to match, so it correctly reports `UNKNOWN` rather than
the placeholder. Reconstructing the real value would mean storing the real
value, which is exactly what redaction exists to prevent. **This is the one
field this trace format cannot replay, by design**, and no other field
(prompt version, retrieved chunk ids + scores, model + params, raw output)
was missing — all were present in the stored record, so nothing had to be
added after the fact.

## Why a public benchmark would have missed this

A public claims/QA benchmark scores free-text answers against a reference
string or a generic "helpfulness/faithfulness" rubric, and every one of these
failures still reads as fluent, on-topic prose that cites a real passage — a
rubric grading tone and topicality would pass trc_00034 and trc_00054 without
noticing the cited sentence and the stated verdict directly contradict each
other. The exclusion-id mislabelling mode is invisible to any benchmark that
only scores the free-text summary, because `cited_exclusion_id` is a
structured field no prose-scoring rubric looks at. And the inconsistency
between trc_00034 and trc_00081 — identical fact pattern, opposite verdicts —
is only visible by reading two traces side by side; a benchmark that scores
each case independently, which is how essentially all of them work, has no
mechanism for noticing that the same input class gets different answers on
different runs.
