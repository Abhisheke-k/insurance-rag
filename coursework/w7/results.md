## Verdict: I'd ship the fixed workflow

Digging into `race_raw.json` rather than trusting the scoreboard: the agent's 3
losses on decision accuracy are misleading in both directions.

**`sequential_flood_e17` "worked" for the wrong reason, on both pipelines.**
Both cite clause `4.1` ("Flood Defence Maintenance") as the denial ground --
not `4.3` (Exclusion Code E-17, the clause that actually governs a *second*
flood within 60 days) or `4.4` (its carve-out for tested defences). `4.1` sits
in the same 550-token chunk as `4.2`'s exclusion-list intro ("this
endorsement does not cover... out of:"), so the stub's negation-cue heuristic
fires on the wrong sentence and happens to land on "denied" anyway. Neither
pipeline evaluated the actual day-count (42 days < 60), the fact this
question turns on. Getting the *label* right here isn't evidence either
pipeline reasoned about the exclusion correctly.

**`malformed_claim_number` is the same underlying inference, with and without
a coin flip.** Agent and fixed retrieve the identical top passage and would
produce the identical raw decision -- but `_summarize_claim`'s stub persona
(`app/llm.py`) carries a seeded "right passage, wrong conclusion" failure
injection (the same simulator that gives Weeks 5-6 real errors to find) that
happens to flip this specific note's hash bucket from `denied` to `covered`.
The agent's persona deliberately does not carry that injection (see the
comment in `app/llm.py` next to `_agent_turn`), so it reports the raw,
un-flipped `denied`. The fixed pipeline's "correct" answer on this row is an
artifact of a bug simulator, not genuine reasoning -- and the row still shows
what the agent's extra step *is* for: `check_assertions` is the only place in
either pipeline that visibly flags `claim_number_format=FAIL`, which is the
real, load-bearing problem with this claim (the notes never state a
CLM-YYYY-NNNNN number). The fixed workflow never surfaces that at all unless
someone remembers to call `run_assertions()` afterward.

**`out_of_scope_theft` fails identically on both.** `summarize_claim()` has no
relevance gate (unlike `/ask`) by design, so a claim entirely outside this
corpus (vehicle theft, no motor cover in this pack) still gets a confident
`covered`. This is a shared gap, not something the agent's extra reasoning
step fixed -- and it's the clearest actionable follow-up this exercise
surfaced: port `/ask`'s `MIN_RELEVANCE` gate into claim summarisation too, in
either pipeline.

**On the two clean-match scenarios (`clear_flood`, `cyber_fire_writeback`),
agent and fixed agree exactly** -- same decision, same citation, same
assertions. `top_k=5` against this five-endorsement corpus already puts the
right clause in front of the model on the first retrieve every time in this
run; the agent's stub persona never actually issued a second `search_policy`
call in any of the five scenarios (every agent row above is exactly 3 LLM
calls: search once, check once, finalize). That is a property of the
**deterministic stub persona**, which is scripted to search exactly once, not
of the loop itself -- the loop enforces *order* (search and check before
finalize), not a search *count*, so a real model genuinely unsure after one
search can still issue a second one. This comparison did not exercise that
path; re-running with `--llm-provider anthropic` against a scenario built to
need it would be the next honest step, not assumed here.

**Conclusion.** For this task -- claim summarisation over a small, mostly-flat
corpus where `top_k=5` already surfaces the deciding clause -- the two
pipelines have the same *decision* quality once you control for the stub's
injected imperfection, and the agent costs **3x the LLM calls** (which would
be 3x the latency and 3x the token spend against a live model) for that same
outcome. I'd ship the fixed workflow (`summarize_claim()` + `run_assertions()`
run together, since the assertions today are computed but not wired into the
live `/summarize-claim` response) as the default path. The agent earns its
keep only where a single retrieve is genuinely insufficient -- a larger or
more fragmented corpus where the right clause sometimes isn't in the first
`top_k`, or a task where self-correction against a failing assertion should
change the retrieval, not just get logged. This corpus is small enough that
neither condition holds today; the fixed workflow is the simpler, cheaper,
equally-reliable choice, and the agent is the one to reach for once the
corpus or the task grows past what one retrieve reliably covers.
